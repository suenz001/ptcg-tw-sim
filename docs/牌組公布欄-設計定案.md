## 3. 資料模型（存 Mongo／Oracle，不存 Firestore）

理由：按讚防灌票需要伺服器權威唯一鍵；原型分類 `classifyDeck` 與賽事歸檔都在 Mongo；admin 管理有現成慣例。Firestore 只放 per-user 私有資料是既有分工。

### collection `deckPosts`

```js
{
  _id: 'dp_' + ...,
  status: 'published' | 'hidden' | 'deleted',   // 皆軟刪
  uid, email,                 // ⚠ 絕不出現在公開回應
  authorName,                 // ≤24
  deckName,                   // ≤40
  entries: [{cardId, count}], // 伺服器重驗後存（去掉 role 等雜欄）
  entriesHash,                // 同人重複投稿去重
  notes,                      // ≤200
  archetype,                  // classifyDeck 快照
  cardTotal: 60,
  tournament: null | { eventId, eventName, finishedAt, placementLabel: '冠軍'|'亞軍'|'四強' },
  likeCount, downloadCount,   // 非正規化快照，權威在明細表
  createdAt, updatedAt,
}
```

### 防灌票的核心：明細表複合唯一鍵

- `deckPostLikes`：`_id = postId + '__' + uid`
- `deckPostDownloads`：`_id = postId + '__' + uid`

按讚＝`insertOne`，DuplicateKey ⇒ 已讚過、不 `$inc`。**每帳號每篇恆為 0 或 1，client 怎麼重放都一樣**。
下載計數同理 ⇒ 語意是「有多少個**不同帳號**拿過」，UI 標成「被 N 位玩家收藏」而非「下載 N 次」。
兩個計數隨時可由明細表 `countDocuments` 對帳重算（admin `recount` 端點）。

⚠ **投稿 immutable**：沒有編輯端點。要改＝刪除重投、讚數歸零 —— 這是防「換皮繼承讚數」的必要設計，不是偷懶。

## 4. 端點（全部包在新 IIFE `registerDeckPosts()`，整體 try/catch fail-silent）

| 端點 | 方法 | 驗證 | 限流 |
|---|---|---|---|
| `/api/deck-posts` | GET | 公開 | 30s TTL 快取 |
| `/api/deck-posts/:id` | GET | 公開；帶 token 時多回 `likedByMe/downloadedByMe` | per-IP 60/min |
| `/api/deck-posts` | POST | verified | 60s 1 篇＋每日 3 篇＋未刪總量 10 篇＋entriesHash 去重＋body 32KB |
| `/api/deck-posts/:id` | DELETE | 本人（軟刪） | per-uid 10/min |
| `/api/deck-posts/:id/like` | POST/DELETE | verified | per-uid 30/min |
| `/api/deck-posts/:id/download` | POST | 有 token 才計數，無 token 回 204 | per-uid 30/min |
| `/api/deck-posts/tournament-eligibility` | GET | verified | per-uid 60s 快取 |
| `/api/deck-posts/tournament-submit` | POST | verified；body 只有 `{eventId}` | per-uid 60s |
| `/api/admin/deck-posts` `/:id/hide` `/:id/restore` `/recount` | GET/POST | `requireFirebaseAdmin` | — |

- **列表 GET 不回 `entries`**（60 張×每頁 20 筆是白流量；v6.119 有「deckEntries 讀放大」教訓）。白名單欄位序列化，**uid/email 絕不外流**。
- 排序 `?sort=new|likes|downloads`（三種明確排序，不做加權熱門演算法）；篩選 `?archetype=&tournamentOnly=1`；分頁 `?page=&pageSize=`。
- **公開 GET 要設 `Cache-Control: no-store`** —— 正式站有 Cloudflare 快取前科（index.json 曾被快取 4 天）。
- 原型分類**必須重用** `app.locals._deckRuleHelpers.classifyDeck`（規則是 admin 私有、前端拿不到；抄第二份違反中央收斂鐵律）。

## 5. 賽事名次投稿：伺服器端零信任驗證

`POST /tournament-submit` body 只有 `{eventId}`（＋可選 notes/authorName）。伺服器：

1. `TARCHIVE.findOne({_id:'arch_'+eventId})`，無 → 404
2. **非社群賽**（Wilson 拍板 ④）
3. `finishedAt` 在 30 天內
4. `app.locals._detectCutPlacements(archive.matches)` → 比對 `tournIdentity` 的 uid：
   `championUid` → 冠軍｜`finals` 有 → 亞軍｜`top4` 有 → 四強｜都沒有 → 403
5. **`placementsOk=false`（推不出名次）→ fail-closed，只開放冠軍投稿**（`championUid` 是明確欄位不靠推導）
6. 牌組直接取 `archive.players[]` 中該 uid 的 `deckEntries`（Wilson 拍板 ②）
7. 查 `{'tournament.eventId':eventId, uid, status:{$ne:'deleted'}}` 擋重複投稿

**client 沒有任何路徑可以自報名次。**

## 6. 前端

- 新頁 `src/routes/deck-posts/+page.svelte`（不塞進已 3645 行的 `/decks`）
- 入口：`/decks` 工具列加「投稿」與「公布欄」；首頁加入口
- **beta 測試站 graceful**：偵測 API 不可用時顯示「此功能僅正式站提供」（比照 `/tournament`）
- 匯入流程：`entries → migrateDeck → splitTwoCardStadiumEntries → newDeck('原名（公布欄）') → upsertDeck → 置頂 → 已登入則 fire download 計數 → validateDeck 不合法給黃字警告但仍匯入`
- 投稿前先跑前端 `validateDeck()` 擋不合法，省往返
- **賽事名次一鍵投稿入口**：錦標賽大廳頂部橫幅（進大廳時查 eligibility）＋名人堂該賽事列小按鈕。**不做賽後結算即時跳窗**（archive 寫入時序複雜，少一個時序 bug 面）
- v1 明細用**文字牌表**，不做 60 張卡圖渲染（`/cards` 全量渲染曾是效能事故源 v6.118）

## 8. 已定案的其餘規則（Fable 建議，Wilson 未反對）

- 投稿期限：賽後 **30 天**（archive 永久保存，日後放寬隨時可以）
- 投稿量：每日 3 篇／每人未刪總量 10 篇
- 開放 notes 說明欄（≤200 字）
- 未登入可瀏覽＋匯入（**不計數**）
- 按讚不加「打過一場」門檻（v1 先觀察；明細表有完整追溯資料，發現灌票再加固 —— **該類修正不進公開 changelog**）
- 頁名「牌組公布欄」，路由 `/deck-posts`

## 9. 明確**不做**的（避免範圍蔓延）

- 留言／評論系統（審核成本全落在 Wilson 一人身上）
- 投稿編輯功能（防換皮繼承讚數）
- 加權熱門演算法／時間衰減（量級撐不起也驗不了）
- 3／4 名區分、純瑞士制名次推導（fail-closed）
- 抄襲偵測（netdeck 是卡牌遊戲文化，60 張全同也無法證明抄襲）
- 關鍵字黑名單（中文變體繞過太容易，是假的安全感）

## 11. 標準輪替與長期維護

- H 標輪掉後舊投稿會變非法 → **不自動下架**，明細顯示「以現行標準驗證」的即時徽章，匯入照常但警告。歷史賽事牌組有保存價值。
